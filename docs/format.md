# VelociDrone 互操作格式与验证边界

适配器是独立编写的 C++ 实现，在本地生成、读取 `.trk`，不连接账号服务，不改写模拟器数据库。Windows 版本使用系统 CNG / BCrypt。模拟器自身仍按其许可证运行。

## 封装与坐标

[官方桌面手册的 Track Editor 部分](https://www.velocidrone.com/desktop_manual)说明：Windows 导出文件位于 Documents，可在 Track Editor → Import Track 中选择文件并按 Import 导入。官方没有公布完整序列化规范，以下区分公开实现、已安装程序的数字测量和测试结果。

文件为 Base64 编码的 AES-128-ECB 密文，PKCS#7 填充。密钥是公开的文件互操作常量，不是账号凭据。解密后的 UTF-8 内容为：

```text
场景数字编号
赛道名称
单行 JSON
附加行 1
附加行 2
```

新文件的附加行为 `0` / `0`；实际原生导出也有 `1` / 非零整数及 `1` / `0`。它们不是起飞坐标。导入保留 JSON 后的原始字节，重新输出保留，不猜测其含义。名称换行转为空格。

JSON 主要有 `gates`、`barriers`，可能还有天气等字段。`pos` 为整数厘米，原生 Y 向上；`rot` 按 W、X、Y、Z 排列并乘 1000；`scale` 为百分比。工程几何仍使用原生 X/Z 平面、Y 高度；中文界面将地面标为 X/Y、高度标为 Z，只改变标签，不交换存储坐标。偏航 0° 朝原生 +Z，90° 朝 +X。Football Stadium = 8，Empty Scene Day = 16。

`gate` 是穿越编号，不能用数组下标代替门序。实际原生数组经常乱序。导入按编号稳定排序；未改变原有步骤顺序时，输出保留原始数组顺序、编号、起终点和未知字段。

## 三类独立数据

- `TrackDocument.gates` 是实体组件，一个三门、叠门或立方框只有一个物理 ID。
- `routeSteps` 是有序飞行步骤，多个 `pass` 可引用同一实体，分别选择格、面、方向。普通 `guide` 只用于规划；明确标记的翻绕检查点也写入原生门序，但不是实体门。
- `takeoff` 是独立起飞架的基点、基点高度、机头方向，不占门序，不是降落点，也不自动成为第一步。

新方梁实体的每次 `pass` 和每个明确标记的翻绕检查点各生成一个 prefab 88；实体全部 N 根梁只写一次 `barriers`，与穿越次数无关。普通引导点不输出检查点。新建路线的第一个原生检查点设置 `start=true` / `finish=true`，表示计圈起终点，不能代替起飞架。示意如下，真实输出另有实体方梁：

```json
{
  "gates": [{
    "prefab": 88,
    "trans": {"pos": [0,12,0], "rot": [500,-500,500,500], "scale": [100,150,150]},
    "gate": 0, "start": true, "finish": true
  }],
  "barriers": [{
    "prefab": 422,
    "trans": {"pos": [0,0,-600], "rot": [1000,0,0,0], "scale": [100,100,100]}
  }]
}
```

程序要求先配置独立起飞架再导出。核对的四份本机原生导出均将 422（`DefaultKDRAStartGrid`）作为独立障碍物，起终点另在 `gates` 中。新起飞架使用 422、缩放 100；它包含多个起飞位，不是单架无人机中心。运行时 `RaceStartPoint1..10` 比基点高约 0.759 m，横向偏移不同，局部旋转均为单位旋转，因此其偏航直接表示机头方向，不加减 90°。

422 实体架面约在基点上方 0.00273 至 0.66565 m。部分 Football Stadium 原生样本的架基点 Y=-0.86 m 是具体世界坐标，不能推导所有场景的统一地面偏移。程序不自动减去 0.86 m，也不交换已有坐标。

导入识别 90（旧 `DefaultStartGrid`）及 422。90 起飞位有局部旋转，读取机头朝向时计入；不改动时完整保留原变换，编辑后换成 422 并保留机头方向。其他已知起飞架系列保留原生数据，姿态未校准时需要重新配置受支持起飞架。缺失或多个起飞架时不擅自选一个。

## 88 实际运行时触发体

0.1.4 改用安装程序中 `assets/race gates/_defaultsquare.prefab` → `TriggerGate` 的实际数字几何，不再把第三方查看器的编辑辅助模型边界当作触发体。

| 属性 | 运行时值 |
| --- | --- |
| 局部中心 | `(0,0,+0.9900000095)` |
| BoxCollider 尺寸 | `(0.0723237768,1.9286329746,1.9286329746)` |
| 局部轴 | X 薄轴、Y 窗口横向、Z 窗口向上；实际接受方向为 −X |
| 类型 | 启用的触发体，挂载 `CheckPoint` |

0.1.5 另外核对了运行时方向判定：`CheckPoint.Start` 用 `resetPosition − originPosition` 得到接受方向，实际 88 的两个引用分别位于 `(-1,0,0.3)` 与 `(0,0,0.3)`，因此沿局部 **−X** 接受，不能把薄轴的 +X 当成接受方向。方向检查要求速度与该向量点积不为负。

路线接受法线 N、横向 R、向上 U 对应四元数矩阵三列 `[-N,-R,U]`，保持右手系。横向、向上缩放为 `round(窗口米数 / 1.9286329746 × 100)`，薄轴缩放 100。根位置为 `窗口中心 − U × 0.9900000095 × 向上缩放 / 100`，再取整厘米。

默认净开口 2.9 × 2.9 m 使用 `[100,150,150]`，触发窗口约 2.89295 m，不能把 145 当成精确 2.9 m。沿世界 +Z 的普通门使用 `[500,-500,500,500]`，q 与 -q 等价。0.1.4 的 +X 映射使新建组件的原生接受方向与编辑器意图相反，0.1.5 已修正；旧工程中方梁、柱的检查点缺少新方向基准标记时，按编辑器意图重新生成。导入原生文件或保留旧原生模型时，读取并保留其原始接受方向，不擅自反转用户赛道。百分比、厘米、四元数千分位导致毫米级及小角度误差，再导入中心允许约厘米级差异。

立方框前、后、左、右、上、下六面独立生成窗口。默认法线朝所选格内部；反向只翻转本次法线和横向，不旋转实体。上/下面使用水平窗口，支持俯冲、爬升、多层反复穿越。这里只校准文件变换及触发体几何，完整竞赛动作仍需人工核对。

转向柱是实体方柱。旁侧窗口目标宽 2.4 m、高等于柱高，中心距离 `柱宽/2+1.55 m`，可选左右；名义净间隔 0.35 m，实际窗口按百分比量化。一个窗口不能独立验证完整绕柱动作。

## 0.1.5 完整绕梁与显式翻绕检查点

`orbit-bar-cw` / `orbit-bar-ccw` 是明确选择的闭环 360° 模板，不代表所有赛道图上的绕梁动作。顺逆时针按沿组件局部 +X 看、+Y 向上、+Z 向右定义。叠门按下格 → 上格 → 下格穿越同一实体；单门绕顶梁后回到同一开口，不伪造上层实体门。需要一边绕立柱、一边进入下一格的推进动作使用下节的独立模板。

仅放两个重合、同方向的连续检查点不能可靠约束完整转圈：运行时触发处理在首次协程让出前同步激活下个门，同一次物理穿越可能连续接收重叠检查点。因此模板明确增加可见的翻绕检查点：单门为 2 次穿门 + 3 个转向控制，叠门为 3 次穿门 + 2 个转向控制，控制点与穿门严格交错编号。它们不增加实体梁，也不是暗中把全部曲线采样点变成门。

这些控制点仍用 `kind="guide"`，但明确设置 `extra.raceCheckpoint=true`、`checkpointWidth` / `checkpointHeight`（默认 0.8 m）及非零 `curveTangent`。切向量使用与 `localGuide` 相同的归一化组件轴，未绑定实体时为世界轴。可选 `checkpointUp` 保存窗口向上方向，包括导入非正方形窗口时的滚转。标记必须为布尔值，尺寸须在 0.1 至 100 m 范围，向量须有限、非零、不能平行；损坏元数据在写文件前报错。

原生输出仅约束这些有限窗口及其接受方向，不编码整条连续圆弧、飞行速度、无人机动力学或完整联赛判定。普通引导点及曲线平滑提示保留在 `.otproj`，不会输出额外门。移除翻绕检查点也会移除对应原生约束；预览曲线无碰撞不等于已验证真实飞行。

无法与实体梁、柱配对的原生 88 被恢复成独立翻绕/路线检查点：无实体 ID，使用世界位置、方向、尺寸和原始数据，不再伪造物理门框。它可能来自用户原生赛道，不能只凭孤立窗口推断它属于哪种绕梁动作。即使没有可编辑实体，只有独立检查点和起飞架的赛道也可保留输出。

## 0.1.6 推进穿越、偏移过门点与实际原生窗口

绕立柱推进与闭环绕横梁不同。`upright-left-up/down`、`upright-right-up/down` 沿立柱连续上升或下降，结束于另一层开口，只有两次实际穿门，不先返回旧开口再升高。两个窗口可以具有相同的接受方向，由中间所选立柱外侧的一个显式翻绕检查点约束绕行侧。并排多门的过门点及引导线也可以同时改变高度、深度，而不强制铺成同一高度的平面 U 形。

每次实际穿门可设置预览用 `extra.apertureU` / `apertureV` 和 `extra.flightTangent`。U/V 是组件面内物理横向、向上方向的半净开口归一化偏移，在 `reverse` 之前解释；程序保留预览净空边距，拒绝把点移入梁内。切向量采用归一化组件轴，变换后的飞行方向必须与物理接受法线同半球，点积大于 0.01，不能用一条反向切线掩盖进出门错误。

这两组几何明确分开：`RouteStepGeometry.position/normal/right/up/openingWidth/openingHeight` 始终描述完整、居中的物理原生窗口；`pathPosition/pathTangent` 描述预览的偏移过门点和斜向飞行。实际门的原生 88 使用前一组，不因 U/V 或斜向切线移到门框之外，也不把触发平面任意倾斜。`.otproj` 保留完整拟合路径；仅重新读取 `.trk` 无法恢复这些预览偏移和每个普通曲线采样点。

立方框的出面也须明确指定。例如从顶部进入、从左面出去使用顶部向下窗口，再用 `face="left", reverse=true` 的向外左面窗口；双层立方框是顶部、层间开口、下层左面。不能为了走向下一组件而旋转整个立方框、将左面出口冒充正面出口。

只有明确标记的关键外侧控制点进入原生门序，例如每次推进绕行的外侧中点；其余拟合引导点保持预览用途，不把全部采样点变成隐藏关卡。实际穿门、关键控制点、方向及空间位置按源步骤严格交错输出。有限窗口可以约束所选绕行侧，但不编码完整连续轨迹，也不等于真实飞行或联赛规则已经验证。

## 保留策略与限制

- `.trk` 没有本项目组合 ID。导入按完整梁结构、颜色、位置、朝向、窗口配对，先试大结构，再将多次检查点关联同一实体。检查重复中央梁，避免误并相邻独立单门。归属只存工程 `extra`，不注入原生自定义字段。
- 移动、复制、删除已配对实体会更新所属全部梁。无窗口引用或无法配对的原生障碍物原样保留，但可能不恢复成可编辑组。对称结构的面名可能归一为几何等价的面/反向组合，世界窗口中心、方向保持。
- 旧 285 等模型同时有实体和检查点，未校准前只保留一次原始穿越；重复或任意面明确报错，请先改用方梁结构。170 旗帜仅兼容导入，不作为新转向柱。未知模型的图标、孔径、中心只作示意，原始数据保留。
- `.otproj` 保留全部引导点；重读 `.trk` 恢复实际穿门和已输出的翻绕检查点，不凭空恢复其余曲线采样点。底图不自动变成模拟器地形或贴图。
- 保留原生 `lap1only`、未知字段、天气、尾部、未改动起飞架。原生替代路线可使用重复编号，UI 以线性步骤显示，未改动保留记录，编辑后不自动推断分支规则。[官方更新记录](https://www.velocidrone.com/news)说明 2025 年 11 月新增首圈专用门和重复门号替代路线，不能随意丢弃这些字段。
- 0.1.3 中有中心线标记的工程保留实体几何，新输出使用校准后的 88。旧 `.trk` 若用了此前未校准的辅助模型变换，可能无法恢复组合，请优先打开原 `.otproj` 再导出。

## 已完成验证

`tests/velocidrone_test.cpp` 使用独立 .NET AES 已知答案密文，覆盖中文、旧 285、90/422、乱序数组、非零尾部、未知字段精确保留，以及 13 色、实际单位梁、全部组合、重复格/面/反向/水平重力窗口、引导点、无引用实体、柱旁多次穿越、删除归属梁、错误输入、原文件保护。

0.1.5 增加顺/逆时针完整绕梁与重力门组合测试：旋转的三种不同颜色实体只输出 31 根梁及一个起飞架，8 次穿门与 5 个翻绕检查点输出 13 个有序原生记录。测试独立按实际局部 −X 规则解码接受方向和世界窗口，核对厘米量化、普通引导点不影响原生输出、自由窗口滚转、损坏元数据拒绝、旧工程方向迁移和原生文件方向精确保留。

0.1.6 增加四种立柱上/下推进、三门/双门的高度与深度变化、标准朝向立方框左侧出口及双层立方框“顶部 → 层间 → 下层左面”的合成回归。五个物理组件仅输出 56 根梁及一个起飞架，12 次穿门与 4 个关键外侧控制点输出 16 条检查记录。测试验证推进不返回旧层、偏移/斜向路径元数据不改变完整原生窗口、原生接受方向正确、反向切线在写文件前拒绝。测试不使用用户原图或私人赛道作为公开夹具。

四份本机真实原生导出分别有 52 / 54 / 33 / 67 个检查点，均只读导入至私有工作目录，再输出、再读取，原始 JSON 完整一致，均识别独立 422。私人赛道和游戏资产不进入开源仓库。

两份独立构造的测试赛道使用场景 16 / 8、两个检查点、八根梁、一个 422，已在安装的 VelociDrone 中通过 Import 导入，且只读确认模拟器保存的测试 JSON 与输入完全相同。

0.1.4 时还用实际 C++ 导出代码生成场景 16 测试赛道，在模拟器界面点击 Import 一次，只读确认新增一条测试记录，JSON 与 C++ 文件完全相同：两个检查点、八根 2218 梁、一个 422。这证明封装与记录被实际模拟器接受；不能把该导入结果当成 0.1.5 新方向和翻绕约束的实际飞行证明。

独立测试赛道已进入原生编辑场景及 F9 试飞流程，但模拟器提示遥控器未配置，未完成实际起飞或逐门飞行。因此场景/导入验证与真实飞行、方向判定、不同版本、完整联赛规则仍分别记录，不能声称已完成全部飞行验证。
